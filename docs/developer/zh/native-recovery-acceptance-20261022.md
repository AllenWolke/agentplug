# 三个示例真实恢复补验：2026-10-22

本项目正式环境已补齐三个示例的通知送达后取消撤回、Java/Python 审批等待时重启续接，以及执行中断后的原收据只读恢复。全部使用本项目原账号、已发布的 0.3.0 Agent 镜像、现有策略与真实模型端点；没有修改业务规则、授权、策略、数据库迁移或历史未知记录。对照项目本轮没有被读取、修改、构建、测试或操作运行环境。

这份补验承接[通知与取消补偿首次启用验收](notification-compensation-acceptance-20261022.md)，具体任务、镜像、行摘要和证据文件 SHA-256 见[补验清单](native-recovery-deployment-20261022.json)。

## 实际验证结果

| 示例 | 审批等待时重启平台 | 执行中断后恢复 | 通知送达后取消 |
| --- | --- | --- | --- |
| Go 运维诊断 | 沿用前轮正式环境通过证据 | 本轮真实暂停、恢复 Agent 容器，丢弃一次已提交通知工具响应；SDK 只读原收据恢复 | 实际送达后撤回，原文与撤回收据保留 |
| Java 工单助手 | 本轮原等待任务重启后仍为 `waiting`，按原检查点审批续接成功 | 同上，未再次发送原通知调用 | 同上 |
| Python 文档问答 | 本轮原等待任务重启后仍为 `waiting`，按原检查点审批续接成功 | 同上，未再次发送原通知调用 | 同上 |

三个验收任务分别为 `native-recovery-20261022-go-v2-run`、`native-recovery-20261022-java-run`、`native-recovery-20261022-python-run`。均使用新的验收会话；Python 显式选择 `tool_loop`，缺省 `direct` 保留。固定协作没有重测或改写，本轮关闭该可选项以节省模型额度。

每个任务分别取得以下原始证据：

1. 按原业务流程进入工具审批，使用本人原密码完成独立确认；Java/Python 在审批等待期间重建本项目平台容器，原任务及检查点身份不变。
2. 通知工具在真实平台提交成功后，短暂暂停 Agent 容器，核对 Docker `Paused=true`，随后恢复。临时本机边界丢弃这一次真实 HTTP 响应，不改变模型或工具返回内容。
3. SDK 查询 `/internal/tool/receipt`，`call_id`、操作摘要和通知标识均与原调用一致。每例只有一次原收据查询、一次产生通知的调用；下一次模型请求在转发之前被拦住，证明业务执行已消费恢复收据，又避免额外模型费用。
4. 核对真实 Kafka 链路：Outbox `published`、投递 `published`、本人收件箱 `delivered`，再取消该新任务。
5. 最终运行 `cancelled`、补偿 `complete`、可信停止证明存在；收件箱为 `withdrawn`，原文与撤回收据保留；模型预留、树预算和会话租约均已关闭。
6. 移除临时边界并恢复原配置后，再次重建平台，三条撤回状态和收据仍可读取。原任务幂等重复提交不改变运行修订，也没有新增模型调用；跨用户事件读取被拒绝。

## 验证范围

本轮中断是实际 Agent 容器暂停/恢复，以及已提交工具的 HTTP 响应丢失；没有进行 Agent 进程崩溃替换、宿主断电或真实供应商发送后的模型丢响应/未知费用注入。不能把本轮结果扩大为这些故障已在正式环境验收。

模型请求、工具调用、Kafka、数据库和通知收据均来自本项目真实运行环境。临时边界只透传原签名请求、丢弃指定新任务的一次响应，并阻止下一次模型发送；不使用受控假模型，不伪造通知、收据或费用，不记录签名头、凭据和请求正文。

首个 Go 探测任务正常完成，但模型未选择通知工具，故保留为“未覆盖目标场景”，没有计作补验通过。之后使用此前已验证的固定沙箱/本人通知组合输入创建新的 Go 验收任务。原任务、结果和用量保留，没有修改其输入、重复提交未知操作或隐藏该笔费用。`notify_me` 沿用既有工具选择语义，验收以实际通知收据为准。
