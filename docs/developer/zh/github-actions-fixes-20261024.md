## 故障原因与修复

### `identity-sql`：知识套件混入独立补偿夹具用例

原知识套件同时运行 `internal/knowledge` 和 `cmd/platform`，其中 `-run TestPostgres` 匹配范围过宽，选中了 `TestPostgresCancellationProgressCompositionDoesNotReadFrozenToolHistory`。该用例需要独立补偿夹具，在知识夹具中会跳过。用户提供的失败回执显示 Go 退出码为 0，必需用例均通过，但存在这项跳过，因此“禁止跳过”的验收门禁正确拒绝通过。

[知识验证驱动](../../../scripts/verify_public_knowledge_postgres.py)改为带起止边界的知识领域正向匹配。源码集合回归确认原有 **54 个知识领域父用例全部保留**，只将上述补偿用例留在原本负责它的专用夹具中；专用 CI 中该用例已实际通过。没有删除用例、允许跳过或降低九个关键包的覆盖率阈值。

同时增加失败摘要，明确报告测试退出码、跳过项、缺失必需项及关键覆盖率状态，避免日志末尾仅显示通过记录而难以判断验收拒绝的原因。

### `conditional-public-contracts`：临时初始化服务被误判为最终数据库就绪

原驱动使用不带主机的 `pg_isready`，探测的是 Unix socket。PostgreSQL 官方镜像初始化时会先启动只接受 socket 连接的临时服务，再停止它并启动最终 TCP 服务。原就绪条件可能在服务切换前通过，紧接着的建 Schema 命令因 socket 消失而失败。

按原顺序冷启动 10 次，实际复现 **1 次建 Schema 连接失败**；另一组 10 次探测也观察到 **2 次 socket 已就绪而 TCP 尚未就绪**。GitHub 原输出隐藏了具体设置阶段异常，公开日志不能直接还原其内部错误；上述竞态是在相同旧驱动路径实际复现的缺陷，修复后完整缓存驱动已通过。

新增[共用就绪与诊断辅助模块](../../../scripts/owned_postgres_fixture.py)，由[缓存契约驱动](../../../scripts/verify_isolated_cache_contracts.py)和[专用 SQL 驱动](../../../scripts/verify_dedicated_postgres_tests.py)共同使用：

- 必须先确认 `127.0.0.1:5432` 的最终服务就绪，再成功查询目标数据库的 `SELECT 1`。
- 只有只读就绪探测可以重复；未增加建表、迁移或业务写入重试。
- 设置失败记录受控阶段名、退出码及脱敏错误摘要；生成的密码和 PostgreSQL DSN 不写入公开诊断。
- 保留原有只读源码挂载、资源限制、所有权校验、临时凭据删除和失败清理要求。

[新增回归用例](../../../tests/release-validation/test_owned_postgres_readiness.py)覆盖临时 socket 误报、目标库尚不可查询、等待超时、诊断脱敏，以及知识用例选择集合。
