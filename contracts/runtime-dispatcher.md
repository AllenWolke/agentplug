# Runtime dispatch and risk boundary

The operator registers named executors through an immutable `ExecutionDispatcher`. A registered descriptor fixes `execution_type` (`tool`, `api`, `code`), `risk` (`read_only`, `write`, `high`) and `timeout_seconds`. Input cannot choose an executor type, change risk, substitute a URL or replace a provider. Duplicate names and malformed registrations fail closed; installing MCP and API in either order preserves previous registrations.

New Tool Observations and transaction audit metadata expose `permission_scope` as the actual gateway-authorized capability resource: `action=tool.invoke`, `resource_type=tool`, and the registered tool name as `resource_id`. Policy and authorization epoch remain separate bindings. This object does not assert permission to arbitrary downstream data or include credentials, source text, or user payload. Historical receipts without original evidence keep it null; a non-null receipt scope for a different action or tool is rejected.

The gateway requires a valid registered descriptor as well as current caller/workload resource authorization and the published tool allowlist. Read-only internal tools run with 1–3 second deadlines; API tools with 1–5 second deadlines; writable/high-risk tools with 1–5 seconds. Policy task deadlines may shorten these allowances. Cancellation is passed to the executor and its guarded HTTP requests. Context deadlines do not provide a hard OS kill for an arbitrary uncooperative provider; hard process termination belongs to the isolated Code runner.

Writable/high-risk operations require an explicit bounded `call_id` and cryptographic operation-bound human confirmation even when the publication omits `require_confirmation`. Publication can additionally require approval for read-only tools. The notification outbox is classified as writable. Unknown MCP risk defaults to write; only operator-verified read-only configurations avoid that minimum approval boundary. Remote annotations cannot downgrade risk. The same risk rule applies to receipt reads; authorization and approval are rechecked before disclosure. Confirmation never grants missing resource access.

The public `notify.self` tool uses the `notify_self` function alias and accepts only `title` and `text` (`contracts/jsonschema/notify-self-payload-v1.json`). Runtime limits are 256 and 4,096 UTF-8 bytes respectively. Its recipient is derived from the current trusted scope and is available only when `principal_type` is `user`; machine principals and caller-supplied recipient fields are rejected. It uses the notification Outbox receipt path, so a completed tool receipt means the request was accepted for delivery, not delivered. It retains the writable-tool `call_id`, human confirmation, current authorization, execution lease, commit fencing, receipt recovery, and observation checks.

Tool input parsing preserves JSON numbers, including integers beyond IEEE-754 precision, so approved payload fingerprints cannot silently change. Existing successful, failed and unknown receipt semantics remain in force. API uses the controlled fixed-endpoint executor; writable API adapters still need their own transport/idempotency/service credential implementation before registration for real business use.

The production SQL invocation ledger uses the shared Audit/Outbox transaction port for execution start, completion, proven pre-submit failure, unknown result, expired preparation/execution, and read-only receipt reconciliation. An audit failure rolls back the corresponding ledger transition and Outbox event; failed start cannot admit a provider call. Audit metadata includes the Run, Step and Call, execution type/risk, permission and policy hashes, authorization epoch, lease generation, database-clock timing, bounded error categories, output size and measured resource fields. It excludes code, input/output bodies, confirmation tokens, credentials and environment variables. Missing historical timing or resource measurements remain unknown. Replaying an already reconciled receipt does not create another execution or audit transition. See `platform/internal/capability/tool_runtime_audit.go`; formal transaction-failure and deployment acceptance remain required.

Code descriptors have a 10–60 second allowance and cannot declare read-only risk. Only the platform's isolated Code runner can register that execution type; arbitrary custom providers claiming Code are rejected. The controller and sandbox are implemented in `workers/code-runtime`: fixed immutable images, non-root disposable containers, read-only root filesystem, no host mounts or network, fixed seccomp, and bounded CPU, memory, processes, temporary storage, time and output. The fixed Landlock guard limits readable library paths and writable per-task temporary paths, closes extra inherited descriptors and rejects unsupported hosts before user code runs. Execution images must be built from this repository, pinned and checked; base language images alone are rejected. The platform issues operation-bound signed permits after current authorization and human approval; receipt reads cannot execute code. Code accepts approved source through stdin without host-path or mount inputs. Domain-authorized external access uses registered API tools, with service credentials kept out of Code. Source implementation and image builds are not deployment or overall acceptance evidence; see `code-runtime.md` for the current boundary.

Go, Python and Java use the existing signed Tool capability API. Each must independently exercise the final real platform boundary and complete Harness. Dispatcher tests or a single SDK's success cannot stand in for three-language formal example acceptance.
