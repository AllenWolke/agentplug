# Public Harness loop v1

Known completed Runtime outcomes (`succeeded`, `failed`, `timeout`, `cancelled`, with `effect=completed`) provide bounded untrusted tool context to the next model round. Go, Python and Java preserve the actual status and error type. This does not authorize automatic retries or another sensitive operation; a new call remains subject to published policy, limits and operation-bound approval. Unknown or unconfirmed effects continue to stop for reconciliation.

Status (2026-10-05): the platform published-policy endpoint and Go, Python and Java SDK loop-limit source are now integrated, including the corresponding generated templates. Platform and Go SDK/example build evidence is available; Python and Java compile/test evidence is still being consolidated and is not claimed here. No overall deployment or real-platform scenario acceptance has been completed. Shared numeric digest fixtures and checkpoint interchange remain acceptance items. Each published Agent remains bound to its language and version.

SDK entry points: Go `CapabilityClient.RunHarness`, Python `CapabilityGatewayClient.run_harness`, Java `CapabilityClient.runHarness` with `HarnessRunner.Options`. Java templates include the shared runner. The stateful loops now persist dispatch phases and reconcile model/tool receipts after interruption. Browser waiting/resume delivery and cumulative budget/degradation controls remain separate acceptance work.

Delivery requirement: Python, Go and Java must each expose the complete public Runtime and Harness capabilities and pass independent real-platform example acceptance. All three use the same enforced platform isolation/permission boundary, versioned protocols and shared conformance fixtures. Partial Go/Python loops or a Java HTTP helper do not satisfy this requirement. Tool/API/approved Python-JavaScript-Shell Code executors must be accessible from each SDK under the same controls.

The public loop uses the existing signed Context, Model, Tool and Checkpoint gateways. Namespace is `harness`, caller-selected bounded workflow key identifies the lineage, schema is `schema://agentplug/harness-loop/v1`. Scope, lease generation, policy, TTL, CAS and audit remain platform-owned. Business code does not access platform storage or provider credentials.

Checkpoint absence has a strict meaning: `checkpoint:null` means no lineage head has ever been created for this scope, namespace and key. An existing head whose requested checkpoint has expired or been pruned returns HTTP `409 STATE_CONTINUITY_LOST`; SDK clients must propagate it and must not convert it to null, renew the old state, or restart model/tool execution. A valid latest checkpoint may coexist with an expired historical revision; loading that historical revision still fails. Explicitly beginning a new business operation uses a new Run. This source-level guard does not replace the signed abnormal-exit recovery protocol or prove that an operation with no checkpoint was never dispatched.

Successful public State load/save responses also include `state_key`, the opaque key derived from the trusted execution scope and requested namespace/key. It is not a resource grant. The platform stop transaction captures up to 128 latest checkpoint references with this key, schema, revision, content hash, execution revision and expiry; it validates real payloads without placing their values in recovery events. Empty, expired, pruned or corrupted state prevents production recovery commit. Internal index tasks use their own verified stop receipts and a separate reference. Signed abnormal-exit dispatch and SDK consumption of these references remain under development.

The State route accepts a separate read form: `{"operation":"load","reference":{...}}`, containing exactly the six captured reference fields and no namespace/key, revision selector or write fields. It rechecks the trusted scope prefix, latest head, real content hash and all immutable facts, including expiry, under the existing current memory.read authority. Historical substitution, foreign scope, unavailable state and reference mutation fail. SDK methods are Go `LoadRecoveryCheckpoint`, Python `load_recovery_checkpoint` and Java `loadRecoveryCheckpoint`; these methods are read primitives, not authorization to restart a business handler. The platform's current-generation stop-reference read port also remains separate from approved-resume references and dispatch.

State fields: `version=harness-loop/v1`, `input_hash`, `phase`, `round`, `tool_count`, `messages`, optional `pending`, `output`, `prompt_hash`, `context_source_hash`, `model_request`, `loop_policy_hash`, `loop_limits`, `loop_deadline_ms`, `tool_repeats` and `repeat_counted_call_id`. The caller's original input/round/tool options keep the existing input digest; effective round/tool ceilings are clamped by the current published Harness policy. Each entry reads `POST /internal/runtime/harness-policy` with `{}` and requires `harness-policy/v1`, a lowercase SHA-256 policy hash, exact service time and bounded limits. Optional `runtime.harness` defaults to 8 rounds, 16 tool calls, 1 repeated semantic call, 300 elapsed seconds and `error`. Resume requires the persisted policy hash and limits to match exactly. Confirmation credentials never enter state. Model steps use stable function step keys; tools preserve the same fixed call ID and arguments across approval pause. Checkpoint operation keys bind expected revision; concurrent writers cannot silently overwrite each other.

Phases: `model` prepares approved Context and records `model_dispatch` before contacting a provider; the receipt records `tool` or `done`. Each tool records `tool_dispatch` before contacting Runtime, then persists its validated Observation context and advances. Explicit `TOOL_CONFIRMATION_REQUIRED` records `approval_required`; it is known to precede execution. A later invocation with no approval returns the same pending operation without another model/tool call. An explicit confirmation token is used once for that pending operation and only the platform decides whether it is valid.

`CapabilityClient.RunHarness` returns pending `run_id` from its verified execution context, not from business/model arguments. The host must pass only the operation fields `run_id`, `name`, `call_id`, `payload` to the human approval API; `model_call_id` is transcript metadata and is not an approval request field. The human preview/password/approve flow yields a bounded token consumed in memory by the host. Durable browser query/approval delivery and Execution waiting/resume integration are pending; returning this object is not by itself a working UI pause/resume protocol.

Each model round calls `/internal/context/prepare` with original durable transcript and selected Function names. It sends only the returned approved/windowed messages to Model; stores Prompt/source hashes and rejects unexpected Prompt changes. Estimate admission and actual provider usage retain their existing distinct meanings. No new direct model billing logic exists in the SDK.

The persisted deadline starts at policy `server_time_ms` and covers the complete loop, including tool approval waits. Each handler also measures elapsed time with a monotonic clock; on a later entry it checks the absolute deadline against the newly returned service time. Model, context, skill, tool and checkpoint request timeouts are capped by the remaining loop time. When a dispatch phase is already persisted, the SDK reads its original receipt before applying an elapsed or changed-policy stop; an unknown receipt remains in reconciliation and is never turned into a synthetic incomplete result. Caller round/tool options may reduce the published ceilings but cannot raise them. Public checkpoint history bounds and payload quotas still apply, and the loop reserves checkpoint capacity before dispatch.

Semantic repeat identity is `SHA-256(canonical JSON [toolName,payload])`; the CallID is deliberately excluded. The SDK increments and checkpoints a repeat count plus `repeat_counted_call_id` immediately before the first real invoke. If that operation pauses for confirmation, resuming the same CallID does not count it again. A completed receipt increments `tool_count` and clears the marker in the same saved transition. Object keys are sorted and string encoding follows Go JSON's HTML-safe escapes; exact cross-language numeric edge cases remain pending shared fixtures and are not yet accepted. Legacy checkpoints with no policy fields and `tool_count>0` are rejected because their repeat history cannot be proven. A legacy dispatch first reads its original receipt; after settlement it persists the result and stops with `HARNESS_STATE_REJECTED` instead of granting fresh tool allowance. A `tool_count==0` legacy checkpoint may be upgraded only at a non-dispatch boundary; dispatch recovery must settle its receipt before that upgrade.

The persistent loop sends one request for each model or tool step. Before model generation it saves `model_dispatch` with the exact request; before tool invocation it saves `tool_dispatch` with the exact pending operation. A subsequent invocation in either dispatch phase queries the matching receipt endpoint. Only a matching completed receipt advances state; missing, running, failed or unknown receipts remain stopped for reconciliation. These rules protect a resumed Harness step, but they do not control retries of the outer Agent execution request.

Platform dispatch has a separate retry layer. Its default policy is one attempt with a five-minute active-generation deadline; a positive runtime-policy `max_attempts` or `task_timeout_seconds` overrides those defaults. The deadline covers attempts and retry waits for that active generation, not a parked waiting Run. The dispatcher uses cancellable exponential waits of 250 ms, 500 ms, 1 s and at most 2 s between eligible Gateway attempts. This limits retry timing but does not prove that replay is safe.

The compatibility HTTP dispatcher now treats network/deadline errors, response-body read errors, every non-2xx response, and malformed or unsupported 2xx envelopes as uncertain. It records the failure and enters the durable stop-confirmation path without issuing another business POST. The compatibility dispatcher has no signed Gateway cancel transport, so an unconfirmed stop remains pending; it is not evidence of remote exit. The Gateway path also stops for untyped network, timeout or malformed-response errors. gRPC maps `DeadlineExceeded`, `Unavailable` and `ResourceExhausted` to an untyped uncertain-transport error, which takes that stop path rather than retrying.

Gateway retries require a valid current-Run terminal `failed` ExecuteResponse (or its validated `CompletedExecutionFailure` wrapper), an explicit retryable error and an authoritative quiescence check. A bare `contract.AppError`, including a non-2xx error carrying `Retryable=true`, proves no terminal handler response and enters stop coordination. Production SQL checks admitted descendants and model/tool settlement under the execution row lock before an eligible retry. Terminal success, failure and cancellation repeat that guard inside the outcome transaction before committing events or releasing the session queue; uncertainty rolls back the outcome and requests stop. A validated terminal envelope does not itself prove absence of effects, and recovery still uses fixed idempotent steps and receipts. RoutingTransport selects one protocol and does not fall back to another transport.

The Python `invoke_tool` convenience method makes up to five short polls only for the explicit `TOOL_INVOCATION_IN_PROGRESS` result using the same call ID. It does not retry an unknown network outcome. Python `generate_with_functions` and Java `generateWithFunctions` are separate in-memory loops; they do not persist the Harness dispatch phases or use its receipt-recovery path. The durable entry points above are required when caller restart or unknown outcomes must be reconciled.

Explicit model budget exhaustion produces a bounded `incomplete` Harness result with `termination_reason=MODEL_BUDGET_EXCEEDED`. A published Harness limit with `limit_behavior=incomplete` produces `termination_reason=HARNESS_LIMIT_EXCEEDED` and `finish_reason` of `elapsed_limit`, `repeated_tool_limit`, `round_limit` or `tool_limit`. Both preserve available settled partial text and usage, drop unexecuted tool calls, and are not full success. With `limit_behavior=error`, a reached Harness limit persists its stop state and raises `HARNESS_LIMIT_EXCEEDED`. The Go operations, Python documents and Java tickets examples preserve the specific model-budget and Harness-limit codes; other partial outcomes map to `HARNESS_INCOMPLETE`. These adapter branches have source coverage, while their full deployed behavior remains part of overall acceptance. Other transport, receipt and contract errors stop or surface as errors; there is no generic partial-success fallback. The active generation shares a task deadline, while enabled production Run-tree admission enforces cumulative token/cost limits for parent and child calls. Source wiring, a prepared policy or a compiled fixture does not prove these gates are deployed: real retry, stop, settlement and budget scenarios remain part of overall acceptance.

Recovered `model_dispatch` queries `/internal/model/receipt` with the exact persisted `model_request`, including approved prepared messages, Prompt hash and stable idempotency key. A matching completed `model-receipt/v1` returns the original result; missing/running/failed/reconcile stops. It never repeats Context preparation or generation. Older dispatch checkpoints lacking this request fail closed. Recovered `tool_dispatch` queries `/internal/tool/receipt` with the exact pending operation and optional fresh confirmation token, never the execution endpoint. Only a bound `tool-receipt/v1` completed response with matching `runtime-observation/v1` advances the transcript/checkpoint. Missing/running/failed/unknown remains stopped for reconciliation; no automatic execution or repair occurs. If receipt access requires renewed approval, return the same pending operation while retaining `tool_dispatch`, so the next approved continuation still queries rather than executes. Persisted `done` replays after current checkpoint authorization without provider or tool invocation. An incomplete model answer terminates as `incomplete`, not a successful full answer.
